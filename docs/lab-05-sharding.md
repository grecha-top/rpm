# Лабораторная работа №5. Шардирование PostgreSQL

## Цель

Распределить данные backend-сервиса между несколькими экземплярами PostgreSQL и сравнить две стратегии выбора shard:

- `hash(shard_key) % N`
- Consistent Hashing через hash ring

Файлы:

- `docker-compose.shards.yml` - 4 независимых PostgreSQL для эксперимента.
- `internal/sharding/router.go` - router с `hash % N` и consistent hash ring.
- `cmd/lab05/main.go` - runner лабораторной: читает реальные `bookings`, раскладывает их по shard-БД и считает перенос данных.
- `docs/lab-05-sharding-output.txt` - фактический вывод эксперимента.

## Выбор данных

Выбранная сущность: `bookings`.

Shard key: `user_id`.

Почему выбран `user_id`:

- бронирования естественно принадлежат пользователю;
- в сервисе есть реальный запрос `GET /api/users/{id}/bookings`;
- в `GET /api/bookings` есть фильтр `user_id`;
- если все бронирования пользователя лежат на одном shard, запросы по пользователю можно отправлять только в одну БД;
- `user_id` имеет высокую кардинальность и обычно хорошо распределяет данные.

Потенциальный риск: если один пользователь создает очень много бронирований, его shard станет горячим. Для текущих данных распределение получилось равномерным.

## Запуск shard PostgreSQL

Запускаются 4 независимых PostgreSQL:

```bash
docker compose -f docker-compose.shards.yml up -d
```

Подключения:

```text
shard-0: localhost:55440
shard-1: localhost:55441
shard-2: localhost:55442
shard-3: localhost:55443
database: rpm
user: postgres
password: postgres
```

Первые три shard используются как текущая конфигурация, четвертый нужен для эксперимента добавления нового shard.

## Router

Router реализован в `internal/sharding/router.go`.

Простая стратегия:

```go
shardIndex := hash(userID) % len(shards)
```

Consistent hashing:

```text
hash(shard_key) -> точка на кольце -> ближайший shard по часовой стрелке
```

Для более ровного распределения используются virtual nodes. В эксперименте - 128 virtual nodes на shard.

Hash-функция: SHA-256, из первых 8 байт берется `uint64`. Это стабильнее и равномернее для ring, чем простые учебные hash-варианты.

## Загрузка данных

Runner берет реальные строки из основной таблицы сервиса:

```sql
SELECT id, user_id, event_id, status, seats, total, created_at, updated_at
FROM bookings
ORDER BY id
LIMIT 100000;
```

На каждом shard создается таблица:

```sql
CREATE TABLE IF NOT EXISTS bookings_sharded (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    event_id BIGINT NOT NULL,
    status TEXT NOT NULL,
    seats INTEGER NOT NULL,
    total BIGINT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL
);
```

Затем данные физически загружаются в `shard-0`, `shard-1`, `shard-2` по правилу `hash(user_id) % 3`.

Запуск:

```bash
GOCACHE="$PWD/.gocache" go run ./cmd/lab05 -rows 100000 \
  > docs/lab-05-sharding-output.txt
```

## Результаты распределения

Фактическое распределение `bookings` между тремя PostgreSQL:

```text
shard-0 -> 33316 records (33.32%)
shard-1 -> 33437 records (33.44%)
shard-2 -> 33247 records (33.25%)
```

Вывод: для текущих данных `user_id` распределяет записи почти равномерно. Заметного дисбаланса нет.

Consistent hashing для тех же ключей и трех shard:

```text
shard-0 -> 34590 records (34.59%)
shard-1 -> 31583 records (31.58%)
shard-2 -> 33827 records (33.83%)
```

Распределение тоже достаточно ровное. Небольшие отличия нормальны, потому что hash ring не гарантирует идеальные 33.33% на каждый shard.

## Добавление shard: 3 -> 4

Сравнение количества записей, которые должны переехать при добавлении `shard-3`:

```text
hash(key) % N moved: 75142 records (75.14%)
Consistent hashing moved: 27450 records (27.45%)
```

Почему `hash % N` переносит много данных:

- shard считается через остаток от деления;
- при изменении `N` почти у каждого ключа меняется результат;
- старое правило `hash(key) % 3` и новое `hash(key) % 4` дают разные shard для большинства ключей.

Почему Consistent Hashing переносит меньше:

- каждый shard занимает участок на hash ring;
- при добавлении нового shard он забирает только часть диапазонов у соседей;
- ключи вне этих диапазонов остаются на прежних shard.

## Что будет при удалении shard

При `hash % N` удаление shard снова меняет `N`, поэтому большая часть ключей получит новый shard.

При Consistent Hashing переедут в основном ключи удаленного shard. Остальные ключи сохранят расположение.

## Virtual Nodes

Virtual nodes - это несколько точек одного физического shard на hash ring.

Они нужны, чтобы:

- выровнять распределение данных;
- уменьшить риск, что один shard случайно получит слишком большой диапазон кольца;
- сделать добавление и удаление shard более плавным.

В лабораторной используется 128 virtual nodes на shard.

## Итог

Shard - это отдельный экземпляр БД, который хранит часть данных. Shard key - поле, по которому router определяет, где должна лежать запись. В этой лабораторной shard key - `user_id`, потому что многие запросы сервиса работают с бронированиями конкретного пользователя.

Router нужен, чтобы приложение не ходило во все PostgreSQL подряд, а выбирало нужный shard по ключу. Простая стратегия `hash(key) % N` хорошо распределяет данные, но плохо переживает изменение количества shard: при переходе с 3 на 4 PostgreSQL пришлось бы перенести 75.14% записей.

Consistent Hashing решает эту проблему через hash ring. При добавлении нового shard перемещается только часть ключей, в эксперименте - 27.45%. Для нашего сервиса я бы выбрал Consistent Hashing, потому что он сложнее простой modulo-стратегии, но значительно лучше подходит для роста системы.

## Вопросы для самопроверки

Shard - это отдельный узел хранения, например отдельный PostgreSQL, который содержит часть данных.

Shard key - поле, по которому определяется shard для записи.

Случайно распределять записи нельзя, потому что потом невозможно понять, в какую БД идти за конкретной записью без fan-out запроса во все shard.

`hash(key) % N` берет hash от ключа и остаток от деления на количество shard.

Изменение количества shard является проблемой, потому что меняется результат `% N`, и многие записи должны переехать.

Consistent Hash Ring - это кольцо hash-значений, где ключ и shard отображаются в точки на одном пространстве.

При добавлении shard не нужно переносить все данные, потому что новый shard забирает только часть диапазона кольца.

Virtual nodes - несколько виртуальных точек одного shard на кольце. Они улучшают баланс.

Consistent Hashing не гарантирует идеальное распределение, но с virtual nodes обычно дает достаточно ровную картину.

Если один shard станет сильно загруженным, можно добавить shard, увеличить число virtual nodes, поменять shard key или вынести особо горячие ключи отдельной стратегией.
